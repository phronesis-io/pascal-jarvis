# Jarvis 下一阶段长期目标：Codex 前台，Jarvis 后台

**状态：** 产品方向已确认，实施分阶段验证  
**日期：** 2026-08-27  
**一句话目标：** Pascal 在手机或电脑上的 Codex 随时开启一个干净的新任务，
系统自动带上正确且最小的长期上下文、选择合适执行者、在后台推进并用真实证据
收口；除非需要 Pascal 的判断，否则不占用他的注意力。

## 一、为什么现在必须改方向

Jarvis 已经具备长期运行、飞书、日历、跨会话、模型降级、投递、Matter、Intent、
Routine 和工程闭环，但真实使用暴露了一个根本问题：系统活动很多，用户价值没有按
同样速度增长。

- Codex 已经能在电脑和手机上承载新任务、长内容、文件、代码、测试与交付；Jarvis
  再造一个聊天前台，只会增加上下文、界面和维护成本。
- 最近 14 天有 406 条 Memorial，其中 320 条自然过期；大量主动输出没有换来判断
  或行动。
- 跨产品会话可以被扫描，但“读到日志”还没有稳定转化为“知道哪些结论仍然有效”。
- 同一 Matter 的旧决定、重复卡和已完成事项仍可能留在待批状态，说明状态真相没有
  完全闭环。
- 模型路由已经有多条路径，但成本、任务归因、真实负载健康和失败分类还没有统一。

这不是再加几个功能能解决的问题。Jarvis 必须改变工种。

### 最新认知如何进入本方案

Pascal 提供的
[DHH × Lex Fridman #501 讨论整理](https://pcnlty6lw65j.feishu.cn/docx/NKZvdZD7Poy2hsxRKzlcv4Cgn6H)
强化了六个判断，但本方案没有照搬个人开发新项目的经验：

- 聊天流不是复杂异步工作的最佳容器，因此主工作面转向可分任务的 Codex；
- brains 与 hands 必须分权，因此推理上下文、执行沙箱、效果权限和验证收据分离；
- 人是稀缺瓶颈，因此系统先完成工作，再把不可替代的判断攒批交给人；
- 过量系统提示词会损伤能力，因此长期知识进入结构化状态和按需 Context Packet；
- 模型差异必须按“规划、执行、审查”分阶段评测，不能用一个小探针替代真实负载；
- Jarvis 是带历史数据与线上责任的存量系统，因此只做渐进迁移、双轨验收和可回滚切换，
  不做一次性重写。

OpenAI 官方文档也证明这条路线具备现实产品基础：
[Codex Remote](https://learn.chatgpt.com/docs/remote) 已支持从手机发起、引导、审批和审阅
连接电脑上的任务；[Projects and chats](https://learn.chatgpt.com/docs/projects) 建议为不同
结果开启独立 chat，并把长期指导放入项目文件；
[Long-running work](https://learn.chatgpt.com/docs/long-running-work) 则提供目标、并行任务、
权限和完成标准的工作流。Jarvis 不应复制这些前台能力，而应补上它们没有承诺的个人
长期状态、跨产品治理与权威闭环。功能可用性仍受 Codex 发布范围和 workspace 设置影响，
所以必须保留适配层与迁移验收。

## 二、北极星

Jarvis 不再争夺“最好的聊天入口”。它进化为一个大部分时间不可见的个人协作底座：

1. **Codex 是统一交互前台。** Pascal 在电脑或手机上主动开始、拆分、继续和审阅
   实质工作。
2. **Jarvis 是连续性与控制后台。** 它维护 Matter、长期记忆、时间触发、权限、
   注意力政策、执行证据和最终状态。
3. **Git/GitHub 是代码证据平面。** 它维护分支、提交、Diff、PR、Review、CI 和
   Merge；Jarvis 只引用完成跨 Session 连续性所需的最小证据，不复制一套仓库状态。
4. **Lark 是唤醒与外部通信通道。** 它承担少量紧急提醒、日历/联系人/群聊原生
   操作和必要审批，不再承载长篇工作台。
5. **Claude Code、Codex、GPT 和其他 harness 是可替换执行环境。** 它们拥有短期
   Session，不拥有长期产品真相。
6. **Model Runtime 是独立模型平面。** 它按任务、信任、工具、质量、成本和健康
   选择模型；产品逻辑不得直接绑定某个模型或账号。

北极星指标不是消息数、卡片数、模型调用数或合并 PR 数，而是：

> **Pascal 每投入十分钟注意力，系统可靠闭环了多少个有价值的 Matter。**

## 三、正确的产品形态

### 3.1 短 Session，长 Matter

Codex/Claude 的每个任务都是可丢弃的执行窗口；Matter 才是长期工作本身。

```text
Matter: Blog 06
  -> Codex task: 找到真正的问题
  -> Codex task: 审查论证结构
  -> Claude Code session: 修改网站
  -> Lark: Pascal 确认一个不可替代的判断
  -> Jarvis: 合并决策、产物、证据和下一步
```

新 Session 不继承整段历史。Jarvis 为它编译一个 `Context Packet`：

- Matter 的目标与当前阶段；
- 已确认、仍有效的决定；
- 当前任务需要的证据和产物；
- 不得违反的约束；
- 尚未解决的冲突；
- 完成时必须交回的收据。

原始转录仍可审计，但不默认进入提示词。长期连续性来自结构化状态与可检索证据，
不是一个永不结束的大对话。

### 3.2 异步协作，不让人坐着等

复杂工作默认进入一个有边界的 Codex task，而不是占住对话不断汇报工具进度。

```text
acquire Matter/context
  -> run bounded task
  -> verify artifacts/effects
  -> release result receipt
  -> reconcile Matter and pending Items
```

Pascal 可以离开、开另一个任务或第二天再看。只有目标歧义、权限/成本变化或不可逆
选择才打断他。普通研究、整理、测试和修复必须先做完，再交付结果。

### 3.3 Brains 和 hands 分开

模型负责规划、解释和判断候选；确定性代码负责状态迁移、权限检查、外部副作用、
幂等、读回验证和收据。不可信代码、邮件、网页和 Agent 消息不能同时接触私人上下文
与高权限工具。

一次执行至少区分：

- `reasoning_context`：模型可见的最小信息；
- `execution_sandbox`：代码和工具实际运行的位置；
- `effect_authority`：这次允许产生什么副作用；
- `verification_receipt`：谁、何时、用什么权威信号确认结果。

### 3.4 人退出执行回路，保留价值判断

Jarvis 的目标不是更频繁地主动，而是把一批工作推进到只剩最后判断。每天至多形成
一个普通决策批次；紧急、安全和真实时间约束例外。系统健康、自愈和模型降级默认在
后台解决并留下可查收据，不把运维转嫁给 Pascal。

### 3.5 少指令，多契约

提示词不再承担整个系统。稳定原则保持短小；领域事实按需检索；当前任务只收到一份
Context Packet。任何新增系统指令都必须证明它解决了可复现失败，并通过删除实验确认
不是在伤害模型。

对复杂任务，默认采用“一个模型执行、另一个独立模型审查”；简单、可确定验证的任务
不为形式消耗第二次模型调用。

## 四、Jarvis 的生存测试

每项现有或新增能力必须至少提供一种 Codex 单次任务无法独立提供的价值：

1. 跨时间、跨 Session、跨产品的连续性；
2. 用户离线时仍有价值的观察或触发；
3. 对注意力、权限、成本或风险的统一治理；
4. 多执行者之间的状态协调；
5. 外部副作用的权威验证和最终闭环。

五项全不满足，能力不属于 Jarvis：优先交给 Codex，其次退役。代码存在、有测试或
历史上写过 PRD，都不是保留理由。

具体淘汰规则：

- 30 天没有真实使用且不承担安全/恢复职责：默认关闭；
- 60 天仍不能证明用户结果：提交退役审查；
- 连续四周主动打扰的有用率低于 30%：降为静默记忆或批次；
- 新能力若不能删除或合并一项旧复杂度：原则上不进入产品；
- Codex 已提供更好交互，而 Jarvis 只复制界面：直接退役 Jarvis 表层实现。

## 五、进步的标准

### 5.1 用户价值

| 指标 | 目标 | 失败意味着什么 |
|---|---:|---|
| 每个闭环 Matter 需要 Pascal 的消息数 | 连续四周下降 | 系统仍把执行转嫁给人 |
| 重复解释率 | `<5%` 的新 Session 需要重讲已确认事实 | 记忆没有形成可用连续性 |
| 普通主动打扰 | 默认 `<=2/天`，另有一个批次 | Jarvis 仍是通知生成器 |
| 主动打扰有用率 | 四周滚动 `>=70%` | 来源应降级或退役 |
| 每日普通待批耗时 | `<=10 分钟` | Agent 没有先完成可代劳工作 |

“有用”必须有后续行动、明确保留反馈或用户主动引用之一；送达、已读和非空回执都
不单独算有用。

### 5.2 连续性与记忆

| 指标 | 目标 |
|---|---:|
| Codex/Claude 新任务绑定正确 Matter | `>=95%`，不确定时不自动绑定 |
| Context Packet 中可追溯陈述 | `100%` 带来源或权威对象 |
| 已确认决定召回 | `>=95%` 的回放样本正确出现 |
| 已失效决定误注入 | `0` |
| 原始工具输出默认进入提示词 | `0` |

记忆质量按“正确、相关、仍有效”衡量，不按索引 turn 数和文件数衡量。

### 5.3 状态真相

以下是硬不变量，不接受平均值：

- 每个 Matter 至多一个开放决策；
- Matter 完成后，相关旧卡、Intent 和 Handoff 在一个协调周期内进入终态；
- 用户回答一次，所有可见副本收口；
- 没有收据就没有“完成”；
- informational Item 超过 24 小时仍占据活队列的数量为零；
- 同一外部副作用不会因重试执行两次。

### 5.4 模型与成本

| 指标 | 目标 |
|---|---:|
| 模型调用归因到 task、Matter、provider、model | `100%` |
| 未记录成本的付费路由 | `0`，或明确标为 unknown |
| 无工具安全任务的降级收口 | `95%` 在 120 秒内得到结果或明确失败 |
| 真实请求失败却被小探针覆盖为健康 | `0` |
| 每个有用结果的等价模型成本 | 连续四周下降 |
| Context Packet token | 在连续性评测不下降前提下，较当前 P50 降低 `>=70%` |

每日绝对预算由 Pascal 设置；预算耗尽时，系统必须降级、排队或静默，不得用任务重试
制造新的额度风暴。

### 5.5 安全与权限

- 对外、破坏性、权限、费用和正式承诺操作保持显式授权；
- 外部动作完成率只由权威读回计算；
- 私人记忆不进入群聊、公开广播或不可信输入任务；
- 模型进程只得到当前路由所需凭证；
- 不可信 hands 与私人 brains 不在同一权限域；
- 密钥泄露、错误目标、虚假完成目标均为零。

### 5.6 工程与简单性

- 维护性预算必须逐季下降，不能只把当前巨型函数合法化；
- 新架构迁移采用兼容适配与可回放证据，不对存量系统做无保护重写；
- 一个功能只有在本地测试、CI、独立审查、发布、运行验证和上线后观察全部通过后
  才算完成；
- 自动自愈成功不打扰用户；同类不可自愈事故一天最多一次可理解告警；
- 能力清单必须包含 `keep / quiet / replace-with-codex / retire` 的产品判断，而不只是
  “是否有测试”。

## 六、分阶段路线

### Phase 0：Truth and Quiet

先修历史状态和度量，不迁移界面。

- 重算并关闭过期、重复、已完成 Matter 的 Memorial/Intent/Handoff；
- 主动输出默认收紧为“需要判断、确定紧急、明显高价值”三类；
- 模型调用补齐 task/Matter/成本归因；
- 把 175 项能力做第一次产品生存审查；
- 修复生产机本地测试假红、私人文件权限和恢复文档漂移。

**准出：** 连续 14 天零重复开放决策、零已完成 Matter 残留待批，普通主动打扰
不超过目标且没有漏掉安全/时间提醒。

### Phase 1：Codex Frontstage Contract

- 定义稳定、provider-neutral 的 Context Packet 与 Result Receipt；
- 为 Codex 提供 Matter 查询、认领、继续、释放和结果回写入口；
- 新 Codex task 默认是新执行 Session，不复用无限增长的大上下文；
- Lark 的长卡改成一句唤醒和可选链接/标识，完整工作留在 Codex；
- 不依赖未公开的 Codex 内部格式，适配器失败时不损伤 Matter 真相。

**准出：** 手机和电脑各完成至少 20 次真实继续任务；正确 Matter 绑定率达到目标，
中途更换入口不要求 Pascal 重讲背景。

每次成功释放的真实任务至多问一次简短验收；忽略即永久跳过，不追问。只有 Pascal
明确回复 `顺` 或有限问题标签，才由确定性代码写入样本；原话和运行收据一起保留，
Agent 不能提供评分、评审者身份或从称赞/沉默中推断通过。每个连接器版本独立积累
20+20 样本，失败版本修复并升版后重新验证，不能拿旧样本替新实现背书。

**2026-08-28 生产检查点：** Phase 0 协议和 Phase 1 本地 Codex 连接层已随
PR #129--#131 上线，并通过同版本 MCP、组件、投递和发布收据验证；这仍不等于
Phase 1 准出。`core.matter_runs` 提供单 Matter 原子租约、续租、超时恢复和不可覆盖的运行
收据；`core.matter_context` 生成带来源引用、权限边界和摘要指纹的
`jarvis.context-packet.v2`；`core.matter_executor` 让 Claude/Codex 共用同一条
acquire/run/release 路径。产物必须在 workspace 内存在并按内容哈希，外部动作必须引用
当前 Delegation 的可信证据。模型最后一句和进程退出码只作为未验证叙述，Matter 不会
自动完成。`core.codex_frontstage` 和 `core.codex_mcp` 通过官方 MCP v2 SDK 暴露
search/create/start/renew/release/abort/health；`plugins/jarvis-matters` 让 Codex
发现这条能力而不读取其内部 task 文件。当前还欠桌面/手机各 20 次真实接受测试、
完整的 Model Runtime 收口，以及可由 Codex 宿主直接打开任务的已验证唤醒适配。

**2026-08-27 后续工程检查点：** `jarvis_matter_continue` 已把查找、消歧、认领和
Context Packet 合成一个自然继续入口；歧义时不绑定。Lark 交接只给稳定 Matter
短语，不伪造 Codex 深链。`core.matter_closure` 在明确 owner 完成确认后，先统一收掉
关联 Intent、Item 和 Handoff，再把 Matter 标记完成；活跃 Run、Job、Delegation
继续阻断，Result Receipt 仍不能自动完成 Matter。以上已在生产部署；Phase 1 的
桌面/手机 20+20 真实准出证据仍未满足。

**2026-08-27 验收入口检查点：** `core.frontstage_acceptance` 与 Codex MCP 已补齐
一次性提示和显式 owner 反馈入口。提示状态写入 Matter Run，重复调用不会重复打扰；
只有成功、收据有效且记录了 desktop/mobile 的运行可参与。`顺` 与五个问题标签由
固定解析器映射，原话、真实 surface 与提示时连接器版本不可覆盖地保存，迟到回复
不会污染新版本统计；样本按 `jarvis-matters 0.3.1` 重新起算。
这关闭了“有 20+20 门禁但手机用户无法自然提交证据”的产品断点；真实样本仍须在
发布后逐次产生，不能由测试或 Agent 补造。

### Phase 2：Memory Compiler

- **仓库实现、发布和首轮真实数据修复已完成，长期回放指标仍待积累。** 原始会话只做审计源；
- `core.memory_compiler` 从 Codex、Claude Code 和 owner-private Lark 提取
  带精确引文的事实、决定、产物、待办、约束和偏好；
- owner 原话可成为有效记忆，assistant 原话只能成为候选；新决定可替代旧决定，
  事实冲突会同时停用直到显式人工选择；
- Matter Context Packet 只编译该 Matter 的当前有效 claim；默认提示词不再注入原始
  session tail、历史搜索结果或旧 `cross_session_digest.md`；
- 旧“跨会话动态”模型卡、PR/time/近重复过滤链已删除，只有确定性发现的新冲突才
  进入 ambient ledger。

**准出：** 记忆回放集达到召回/失效指标，提示词显著缩小且任务质量不下降。

**2026-08-28 生产检查点：** PR #130--#131 修复了上下文依赖式短回复和模型语义
扩写越权。生产修复后 9/9 条 active owner claim 都逐字匹配保留的 owner 引文，
assistant candidate 为 active 的数量为零，冲突为零。该证据证明首轮迁移正确，
但不能代替后续跨产品召回率、失效误注入和 token 缩减回放。

### Phase 3：Model Runtime

- 把分散在 shell、heartbeat 和 fallback 的模型决策收口到一个运行时；
- 真实负载健康、额度、成本、信任、工具能力和上游独立性共同决定路由；
- 重要任务跨模型审查；简单任务由确定性验证收口；
- provider 故障按 provider 处理，不污染业务任务断路器。

**准出：** 所有调用可归因，降级满足时限，单个坏路由不能拖垮调度器。

### Phase 4：Async Personal Organization

- Routine 只保留 1 到 2 条经真实使用确认的高价值节奏；
- L3 观察先形成证据和 Proposal，再由人决定价值；
- Jarvis 把工作推进到最后判断，而不是把新发现原样扔给 Pascal；
- 日常回顾按 Matter 结果组织，不按 Agent 活动量组织。

**2026-08-27 工程检查点：** `core.matter_review` 已把“本周形成的结果、已有执行
收据但尚未 owner 收口、卡住/等待、下一步”做成同一个只读结果模型；Codex 通过
`jarvis_matter_review` 查询，每周飞书卡只做一次有界渲染。旧周回顾的模型调用、
TaskManager 自动 decay/defer/archive 和活动量叙事已删除。只有
`matter_closure_completed` 算完成，Result Receipt 仍只能进入待收口。Routine 保留
哪 1 到 2 条以及 L3 Proposal 的价值判断仍须由真实使用和 Pascal 决定。

**准出：** Pascal 明显减少重复解释和运维，系统在更少消息下闭环更多 Matter。

## 七、反例与边界

这一方向不等于“把一切塞进 Codex”。

- Codex 的 Session 历史不是长期真相；Jarvis 的 Matter 和收据仍需独立、可迁移。
- 手机 Codex 能使用，不等于它已经提供可靠主动唤醒、日历原生操作或外部群聊；
  未验证前，Lark 保留这些职责。
- DHH 的高并行经验来自新项目和单人主导；Jarvis 是有历史数据和真实运行责任的存量
  系统，必须采用渐进迁移、双读验证和可回滚切换，不能一次 vibe rewrite。
- 少提示词不等于无约束。权限、领域不变量、收据和测试应进入代码与结构化协议，
  而不是被删除。
- Agent review 不能替代人的价值判断；人退出的是执行等待，不是产品方向和高风险授权。

## 八、最终状态

当 Jarvis 真正进步后，Pascal 的主观感受应该是：

- 我可以在手机或电脑的 Codex 随手开一个新任务，不怕上下文丢失；
- 我照常用 Git 看 Diff、PR 和 CI，不需要在 Jarvis 里维护第二份工程看板；
- 它知道我已经决定过什么，但不会把所有历史倒给我；
- 它先做完能做的，只在真正需要我时找我；
- 我不需要知道这次背后是 Claude、GPT 还是别的模型；
- 一件事完成后，旧提醒、旧卡片和旧 Session 会一起安静收口；
- 系统越来越少打扰、越来越少需要维护，却越来越能把事情完成。

Jarvis 最终不是一个更显眼的 Agent，而是一套让所有 Agent 能围绕同一个人、同一组
长期目标可靠协作的个人基础设施。
