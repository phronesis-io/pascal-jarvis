## REQ-80 错误摘要落盘 + 轮转加深
现状：claude_call（heartbeat.py:513-626）失败时 err_text 只进 self._log 截 300 字；三处消费空串的 emit（heavy :325-326、批量 :1022-1023、parse_failed :1164-1166）均无错误字段。bot.sh 轮转 3 代×500KB（:73-80 启动、:1275-1289 watchdog）。
改法：
1. 模块级 `_SECRET_RE`（sk-…/Bearer …/token|secret|api_key|password=…）+ `_error_excerpt(text, limit=500)`：首个非空行 + 剥密 + 截断。
2. `self._last_call_error` 实例属性：claude_call 开头重置；非零退出存 err_text；`__KILLED__` 返回前清空（killed 不带 error）；timeout 存 "claude call timed out (Ns)"；两个 except 存 str(e)/"claude CLI not found"。
3. 三处 emit 加 `error=_error_excerpt(self._last_call_error)`；parse_failed 处用 `"envelope unparseable; head: "+raw[:300]`。task_timeout 事件已带 timeout_s 不另加。
4. bot.sh 两处轮转改 for 循环 7→8 代（jarvis.log 在仓库目录不受 /tmp 清理影响）。
测试：_error_excerpt 单测（首行/截断/redacted）；批量失败带摘要且不泄 sk-；parse_failed 带 head:；killed 无 error 字段。
风险：sched_events 行变长 ≤500B 可接受；emit never-raises。

## REQ-83 calendar 失败/空日程区分 + user 探针
现状：calendar_sync_pre.sh:43 吞错不看退出码；:235 tee 无条件覆盖缓存；calendar_sync_post.py:103-117 总从 RAW_CACHE 重写并刷新 synced 时戳（失败让 post 跑会把旧数据洗成新时戳）→ 失败时 pre 必须空 stdout+非零退出（post 不跑，heartbeat 记 pre_nonzero，watermarks 连续 3 次 ⚠️）。告警去重继承 self_diagnostic_post 的 .diag_last_alert.json 全局 4h 窗。
改法：
1. 抓取循环计 _fetch_fail（stderr 收进 tmp/.calsync_err，每轮先清空）；任一天失败即整轮判失败（token 失效 30 天全挂；单日瞬时失败保守保留旧快照 30min）。
2. 失败分支：stderr 报一行（含错误摘要 200 字）→ python 幂等插入陈旧标注（"⚠️ 日历同步失败，以下数据截至 {上次成功 synced 时戳}…"，先 strip 旧标注防叠加）→ exit 1。成功路径原样（成功重写自然抹掉标注）。
3. self_diagnostic_pre.sh Calendar 段后加 user-token 探针：lark-cli calendar +agenda --as user 查未来 1h，失败输出 ⚠️ 行（含"需要跑 lark-cli auth login"提示，_GATE_TRIGGERS 会脱敏 auth 失败细节）。
测试：新增 test_calendar_sync_failover.py（假 lark-cli 于 tmp PATH）：失败→非零/空 stdout/旧文件保留+标注；两次失败标注幂等；成功→标注消失缓存更新；空日程→正常 "(no events)"。
风险：pre 有 60s 硬顶；calendar-sync 在 PRIORITY 永不被熔断只 30min 重试；标注是引用行不影响 generate_calendar_intents 解析。lark-cli exit 0 但错误 JSON 的形态由探针独立覆盖（本轮不加 parse 层 code 检查）。
