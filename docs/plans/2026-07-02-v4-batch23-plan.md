## 0. 关键实况（影响 REQ-85 设计）

- **在产请假事件不是 00:00-00:00 全天块**：它是跨 6/24→7/11 的带时刻多天事件（`start_iso=2026-06-24T12:00:00Z`, `end_iso=2026-07-11T12:30:00Z`，每天同一 `event_id d6107745-…`），每天渲染成 `20:00-20:30`。所以 85.1 全天过滤救不了请假，主修是 85.2 的按事件+日期范围键控；85.1 仍做（真全天事件走 `start.get('date')` 回退路径渲染 00:00-00:00，见 calendar_sync_pre.sh:81-88），作为第二道防线。
- DB 实况：请假 prep 15 行全 cancelled，key `cal:2026-06-24:请假` … `cal:2026-07-08:请假`；churn = 每日新 key + 人工删行后 30min sync 重建（`_load_cal_index` 只防"行还在"）。
- REQ-90 黑洞行确认：`int_879cb1472b` / `int_d9aa5c5668`（context, executed, closure none, closed_at 空）——`_on_moment_terminal`(:920) → `_spawn_closure_followup`(:947) policy followup=None 直接 return，什么都不写。
- `cal:` tag 除 intentions.py 和测试外全仓无消费者，改语义安全。

## 批次 2（意图引擎）

### REQ-85(a) 全天状态块跳过（Pass 1 过滤）

- intentions.py 常量区（:107-124 附近）加 `_STATUS_BLOCK_RE = re.compile(r"请假|婚假|年假|休假|调休|leave|OOO|status", re.IGNORECASE)`。
- Pass 1 `event_match` 解析成功后（:1317-1323 之间）：`start_time=="00:00" and end_time=="00:00" and _STATUS_BLOCK_RE.search(f"{title} {details}")` → continue（stderr 记一行），不进 by_date。
- 在 Pass 1（而非 Pass 2）过滤是刻意的：状态块进 by_date 会污染 carry 的 first-leave 锚点（:1494-1499 取当天最早未来事件）。状态块不该产生 prep/closure/carry 任何一样。
- 防误杀边界：`00:00-08:00 红眼航班`（无关键词）不过滤；`14:00-15:00 请假面谈`（非全天）不过滤。

### REQ-85(b) 按事件真实起始日键控（主修）

- `generate_calendar_intents(calendar_md, event_map=None)` 加可选参数；默认 `_load_event_map()` 读 `ROOT/"calendar_event_mapping.json"`（pre 脚本 :122-154 已写出 event_id/date/time/summary/start_iso/end_iso，无需改 shell）。读失败 → 空 map，fail-open 回退现行为。
- 索引 `(date, time_str) → entry`，歧义用 `title.startswith(summary)` 消解（markdown title 可能带 `@ 地点` 后缀）。
- Pass 1 每事件查 map 拿 start_iso/end_iso（**必须 `.replace('Z','+00:00')` 再 fromisoformat，转 +8 本地**，try/except 回退单日处理）：
  - `current_date > true_start_date` → 多天事件"续日"行，continue（stderr log）。
  - `current_date == true_start_date` 且跨天 → end_iso 存进事件 dict，Pass 2 closure 的 event_end_dt / expires_at 用真实结束时间（:1421-1424、:1462）。
- **key 格式一字不改**（仍 `cal:{date}:{title[:20]}`，date 语义变为"事件真实起始日"）。多天事件只有起始日行建 key；事件开跑后被 past-event skip（:1341）拦住永不再生成 → 请假 7/2 起零生成。
- 不用范围型新 key 的原因：30 天滚动窗口下"可见首日"每天变，含可见端点的 key 每天都新——复刻要修的 bug。锚真实起始日在事件开始前天然稳定。每日例会不误合并：recurring instance 的 start_iso 日期=渲染日，不会被判续日（这是选 mapping 方案而非"连续日期同标题合并"启发式的决定性理由）。

**dedup key 兼容（零迁移）**：单日事件新旧 key 逐字节相同；多天事件是"少生成"不是"换 key 生成"。已 cancel 旧行不复活的两层保证：① 请假 true_start 已过，生成代码走不到 key 查询；② 通用兜底——起始日建 prep 前做范围回退查重：`for d in [true_start_date .. min(end_date, start+30d)]: 若 cal:{d}:{title[:20]} 在 existing_tags → 不建`（`_load_cal_index` 本就吃全状态含 cancelled）。只读旧 key、只写起始日 key。旧行自然老化，无需清理脚本。

### REQ-85(c) date 类 prep 静默过期留痕

- `cleanup_expired()`（:492-501）：裸 UPDATE 改为先 SELECT 再 UPDATE，对每行 `_emit_intent("intent_expired", id, reason="expires_at_lapsed", …)`（_emit_intent :66 never-raises；包 try 防 DB-lock，沿用 :597-607 惯例）。
- 批次 1 的 skip 汇总消费者需同时收 `intent_expired` 且 `reason=="expires_at_lapsed"`（现有该事件有 storm_class/retries_exhausted/closure_stale 三种 reason，按 reason 区分；expiry 只进汇总不进补发）。

### REQ-90 闭环边角 3 件

1. **context executed → na**：`_on_moment_terminal`（:920-944）guard 通过后、spawn 前：`pol=CLOSURE_POLICY[category]`，若 `pol["followup"] is None` → `UPDATE … SET closure_status='na', closed_at=now, closure_result='no-followup policy (category=context)' WHERE id=? AND closure_status='none'` + emit `intent_closure outcome=na via=policy`，return。guard 的 closure_status=='none' 前置保证幂等。
   一次性脚本 `scripts/backfill_req90_context_closures.py`：对两个黑洞行执行同 UPDATE（加 `AND closure_status NOT IN ('done','recorded','na')`），默认 --dry-run。
2. **cron 拒收 closure_question**：`create_intent`（:337-347 附近）：cron + closure_question → stderr 记一行 + `closure_question=""`。coerce 不 raise。
3. **done+空 result coerce**：`record_closure`（:1031-1036 附近）：`outcome=="done" and not str(result).strip()` → `outcome="na"` + stderr。不 raise。事件以 coerce 后 outcome emit。

## 批次 3（心跳核心，与批次 2 不同天上）

### REQ-79.1 去连坐 + 共享级冷却

- 常量（heartbeat.py :181 附近）：`SHARED_FAIL_THRESHOLD=3, SHARED_BACKOFF_BASE=300, SHARED_BACKOFF_MAX=3600`；状态键 `state["__shared_call__"]={consecutive_failures,last_failure,backoff_until}`。**与 `__envelope_parse__` 分开的 key**（envelope 破→未来驱动 79.2 钳批；调用失败→驱动退避；共用会让 API 故障误触拆批=红线）。退避 3→5min, 4→10min, …, ≥7→60min 封顶（1h << CRON_STALENESS 6h，退避不可能把 occurrence 拖成 stale-skip）。
- `if not raw:` 分支重写（镜像 :1146-1180）：每任务回拨 last_run 快重试、记 last_status、照旧 emit task_timeout/task_finish failed；**删** per-task record_failure、删 :1012-1014 PRIORITY 豁免（成死代码）、删 tripped_names 块；共享 streak+1（按失败周期计数，每次进分支只 +1），达阈值算 backoff_until，emit `shared_call_backoff`；保留 `_ack_failed_posts`、save_state、return ""。`__KILLED__` 分支在上方先 return 不计入。
- 成功清零：raw 非空后（:1041 前）`state.pop("__shared_call__", None)`——只要 Claude 有任何回应（哪怕 envelope 解析失败）链路即通。
- 退避闸门：`_run_cycle_locked` 算完 due_tasks 后、priority/regular 切分（:800）前：backoff 生效期只保留 TIER0_TASKS（calendar-sync 直连不碰 Claude，且是 REQ-83 上游），其余跳过——**放在 pre-script 之前**（intention-check 的 pre 有 mark_triggered/inflight 副作用，不跑就不欠对账债）；last_run 不动，解除后自然到期，MAX_BATCH_SIZE 削峰。heavy solo 不豁免；force 路径同样受闸；每周期只 emit 一条聚合 skip 事件（task="*"）。
- PRIORITY 豁免去留：:1012-1014 删；:765/:835/:317 保留（per-task 熔断仍服务真正的单任务故障）。PRIORITY 不豁免共享退避（豁免=对挂掉的 API 每分钟继续打）。
- heavy solo 的 not-raw 失败（:305-331）不喂共享计数器（900s 重任务超时是任务级信号）。

### REQ-79.2（79.1 观察一周后，约 7/9+；仅冻结设计）

- 触发：`__envelope_parse__.consecutive_failures >= 3`；`__shared_call__` 永不触发。
- 改法：把 :935-1194 提取为 `_run_batch(runnable, …) -> parse_ok`（纯搬移）；钳制模式按 last_run 最陈旧取前 2（**PRIORITY 一并纳入取 2**，否则 3 个 PRIORITY 又凑成 envelope），其余 emit `task_skip reason=parse_clamp_deferred`；每任务单元素调 `_run_batch`（n==1 走直接格式无 envelope）。n==1 成功走 :1193 pop 自动回全批。实施前验证：intention-check n==1 时 intentions_post.py 吃单任务 raw 的路径完好。
- 成本自查：钳制期每周期至多 2 调用 vs 正常 1，首次成功即退出，非持续放大。
